# Reproducibility Reviewer

## Summary
LATTICE presents a multimodal spatial omics integration framework with reasonable methodological design, but reproducibility is significantly hampered by the unavailability of the primary dataset and incomplete specification of critical procedural steps. The authors provide detailed hyperparameters and implementation notes in the appendices, but the private melanoma cohort (54,912 spots across 11 samples) cannot be accessed, making end-to-end reproduction impossible for the main results. Code availability is promised as supplementary material but not yet deposited at a versioned, citable location. The upstream pipelines (ReCAST and SARSIM) are insufficiently documented for independent implementation. While the authors acknowledge data restrictions and provide some reproducibility artifacts (Slurm logs, dependency manifests, seeds), these do not substitute for access to the processed feature matrices or a public benchmark dataset.

## Strengths
- Detailed hyperparameter specification in Appendix H (learning rate, weight decay, masking ratio, loss weights, graph k, architecture dimensions) enables configuration replication for anyone with the input data.
- Reproducibility disclosures in Appendix G explicitly state data-use agreements, IRB oversight, compute resources (CPU-only, 16 cores, 128 GB RAM), wall-clock times (~8 minutes per sample), and early-stopping ranges (36–63 epochs, mean 45.2), supporting feasibility assessment.
- Random seeds documented: single-sample runs use global_seed=42; joint multisample analysis uses 11 analysis seeds {7, 11, 19, 23, 29, 31, 37, 41, 43, 47, 53}, enabling reproducibility across runs.
- Dependency pinning mentioned (environment.yml, requirements.txt) and third-party licenses noted (BSD for PyTorch, MIT for PyTorch Geometric), supporting environment reconstruction.
- Training procedure fully specified: full-graph optimization, AdamW with gradient clipping, early stopping with patience=20, validation fraction=0.1, node-level train/validation split, deterministic cuDNN flags when CUDA used.

## Weaknesses
- Primary dataset is private and explicitly non-redistributable: 'The cohort tensors are de-identified clinical biospecimen-derived profiles under a collaborator institution's proprietary agreement, cannot be redistributed publicly, and have no public five-modality substitute at this lattice resolution' (Appendix G.1). This is a HARD blocker for end-to-end reproduction of main results (Table 2, Figures 2–6).
- ReCAST pipeline is described as 'an internal engineering pipeline' (Appendix F) with only high-level scope statements ('standardizes modality-level inputs', 'runs cross-modality gene and feature harmonization'). No pseudocode, source code link, or detailed algorithm is provided. The five-way gene intersection, harmonization procedure, and quality-control thresholds are not specified, making it impossible to reconstruct the input tensors X independently.
- SARSIM is cited as a concurrent preprint (ref. [4], 'bioRxiv, 2026') with no DOI or stable link. Its role in producing 'spatially anchored regulatory projections and overlap-gene artifacts' (Appendix F) is stated but not detailed. The 'overlap_genes.txt' constraint used for harmonization is mentioned but not deposited or defined.
- Code availability is promised but not yet deposited: 'We include anonymized code, Slurm driver scripts, pinned dependency manifests, and run snapshots as supplementary material' (Appendix G.1), but no repository URL, commit hash, or DOI is provided in the manuscript. Supplementary materials are not accessible to reviewers at submission time.
- Processed feature matrices (X, spatial coordinates S) are not deposited. The manuscript states 'The raw data cannot be publicly released because of institutional data-use and privacy restrictions' (Section 4.1), but does not clarify whether de-identified processed tensors (after harmonization and gene intersection) could be released or whether they remain proprietary.
- Upstream pipeline order and dependencies are unclear. The text states 'ReCAST performs preprocessing and harmonization, SARSIM performs spatially anchored regulatory projection, and LATTICE performs graph SSL representation learning' (Section 1), but the exact sequence of operations, which outputs feed which inputs, and how the five modality blocks are assembled from ReCAST and SARSIM outputs is not fully specified. Section 4.1 says 'For every spot, LATTICE assembles five aligned blocks' but does not detail the assembly procedure.
- Modality-specific preprocessing is mentioned but incompletely specified: 'each modality block is standardized with log1p_then_zscore before concatenation' (Appendix H), but the order of operations (log1p then z-score, or z-score then log1p?), handling of zeros, and per-modality vs. global normalization are not clarified. The phrase 'log1p_then_zscore' is a configuration flag name, not a procedure definition.
- Graph construction uses 'union symmetrization' (Appendix H) but this term is not defined. Does it mean (i, j) ∈ E if i ∈ kNN(j) OR j ∈ kNN(i)? This is a critical procedural detail affecting reproducibility.
- Leiden clustering uses 'target cluster count K imported from SARSIM clustering metadata and achieved via a resolution sweep' (Appendix H), but the resolution sweep range, stopping criterion, and how K is determined from SARSIM metadata are not specified. This affects downstream evaluation metrics (ARI, NMI).
- Masking procedure during training is incompletely specified: 'we apply random modality-block masking at the feature level' with ρ=0.15 (Appendix H), but it is unclear whether masking is applied uniformly across all features or per-modality. Does ρ=0.15 mean 15% of entries in Ω are set to 1, or 15% of each modality block? The reconstruction loss uses Huber loss with δ=1.0, but whether this applies to all modalities or only certain ones is not stated.
- Cross-modal alignment pairs are underspecified: 'modality indices zero and one correspond to Visium RNA and spatial ATAC latent branches after graph refinement' (Appendix H). Are only these two modalities aligned, or are all pairs aligned? The notation in Eq. 8 suggests pairwise alignment, but the implementation detail limits it to one pair. This is a material difference affecting the loss computation.
- Validation/test split is mentioned ('validation fraction is set to 0.1, with train/validation masks generated at the node level') but no test set is described. Are embeddings in Table 2 computed on the full dataset (train + validation), or is there a held-out test set? This affects the validity of reported metrics.
- Downstream clustering and evaluation procedure is not fully specified: 'Predicted spot clusters are compared with Space Ranger clustering labels using ARI and NMI when overlap is available' (Appendix H). What does 'when overlap is available' mean? Are some samples excluded from ARI/NMI computation? How is this handled in Table 2 (cohort-level means)?
- Ablation study (Table 3) uses 'full M5 inputs' but does not specify whether the model is retrained for each ablation or whether a single trained model is evaluated under different conditions. The row 'Spatial reg. – ✓ ✓ ✓' suggests spatial regularization is removed during training, but rows with 'Spatial ATAC at eval.' suggest modalities are withheld at test time. The distinction between training-time and test-time ablations is not clearly separated in the table caption or text.

## Questions
- Can the authors deposit the processed, de-identified multimodal feature matrices (X, spatial coordinates S, sample metadata) at a controlled-access repository (e.g., dbGaP, EGA) with a clear access procedure, or confirm that institutional agreements prohibit this?
- What is the exact procedure for ReCAST harmonization? Specifically: (i) how are gene names aligned across modalities? (ii) what are the quality-control thresholds for sample retention (3 samples were excluded; on what criteria)? (iii) how is the five-way gene intersection computed, and what is the distribution of intersection sizes across samples?
- Can the authors provide a stable, versioned link (GitHub commit/tag or Zenodo DOI) to the LATTICE code and supplementary materials, including Slurm scripts and dependency files?
- How is the 'log1p_then_zscore' normalization implemented? Specifically, is it log1p(X) then z-score per feature, or z-score then log1p? Are zeros handled specially?
- What does 'union symmetrization' mean for the kNN graph? Is an edge (i, j) added if i ∈ kNN(j) OR j ∈ kNN(i)?
- In the cross-modal alignment loss (Eq. 8), are all modality pairs aligned, or only Visium RNA and spatial ATAC? If only one pair, why were these two chosen, and how sensitive are results to this choice?
- In Table 3, are the ablation rows (e.g., 'Spatial reg. –') trained from scratch with that component removed, or is a single M5 model evaluated under different conditions? Please clarify the distinction between training-time and test-time ablations.
- How is the Leiden resolution sweep performed to achieve target cluster count K? What is the resolution range, and how is the final resolution selected?
- Are the ARI and NMI values in Table 2 computed on all 54,912 spots, or are some samples excluded due to missing Space Ranger labels? How are cohort-level means computed if sample sizes differ?
- The manuscript states 'LATTICE M1 underperforms RNA-specialized baselines because the architecture and objectives are designed for multimodal representation learning rather than optimization for transcriptomic clustering alone' (Section 4.2). Was LATTICE M1 trained with the same hyperparameters (λ₁, λ₂, λ₃) as M2–M5, or were hyperparameters tuned separately for M1?
- Can the authors clarify whether embeddings Z in Table 2 are computed on the full dataset (train + validation) or on a held-out test set? If train + validation, does this inflate reported metrics?
